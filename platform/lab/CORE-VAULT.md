# Core asset signer custody experiment

The [Metaplex Core Execute instruction](https://www.metaplex.com/docs/smart-contracts/core/execute-asset-signing) permits a live Core asset's authorized owner to invoke an instruction with a signer PDA derived from that asset. Instead of binding a Rewards leaf to the original minter, bind it to this PDA. Then the Rewards program can enforce cumulative vesting while Core enforces who controls the claimant. The app never signs in place of the NFT owner. [Execute implementation at the inspected revision](https://github.com/metaplex-foundation/mpl-core/blob/c8732ac66066ec5174beaaab51f9dabf05089f26/programs/mpl-core/src/processor/execute.rs)

The replay pins public upgradeable Core programdata at finalized slot **465657853** and the Foundation Rewards program at slot **465655227**. It uses a real 14-sibling proof, one shared authority lookup table, and a fresh temporary token account controlled by the asset signer. It simulates an unminted reserve, 30 units claimed at hour 36 by the original owner, direct Core transfer, a rejected seller claim, and 70 remaining units paid to the buyer at day 800. It requires actual token balance deltas, transaction sizes of at most 1,232 bytes and the temporary token account closing. To rerun, use the existing Rewards ELF, then `node platform/lab/fetch-rewards-replay-elf.mjs /tmp/core.so core` and `node platform/lab/replay-core-vault.mjs /path/to/october-reference /tmp/rewards.so /tmp/core.so`.

The intended payout is atomic: Core Execute claims into an SPL account owned by the NFT's PDA, transfers the exact payout to the current owner's token account and closes that temporary account. Creating the fresh temporary account is a separate rent-bearing preparation. Using a fresh account avoids trusting a long-lived token delegate set by an earlier owner. Record the three Execute charges, claimant state rent, temporary-account rent, recipient ATA costs (if missing), transaction signatures, compute limits and any priority fees. Test on a physical wallet with the real v0 packet before promising an affordable user experience.

[The first successful composite replay](https://github.com/chrisjacob/warplets-api/actions/runs/42004780191) recorded a 1,002-byte atomic v0 payout with 14 proof siblings. The three Execute charges added 146,160 lamports to the asset account. This measurement excludes Solana network fees, lookup table setup and claim-state or token-account rent.

**What this experiment leaves open.** A valid slot-to-asset commitment, unbiased delayed-reveal mint flow and protection of unminted asset addresses remain prerequisites. The fixture deliberately uses a controlled test key to bind a reserved slot to a future asset; it proves no randomness or operator fairness. A plugin-free transfer demonstrates basic ownership. Marketplace escrow, permanent delegates, freeze/execute authorities, collection policy, upgrade-authority trust and externally initiated burns need separate tests. Core documents that burning a live asset permanently prevents its signer from executing. Omitting a burn button does not exclude on-chain burns. Any selection must explain stranded or destroyed claims and protect live asset identities.

The extended replay tests a plain asset burn followed by an attempted transfer from its still-funded signer account. It also exercises an experimental **immutable Oracle that rejects burns** on a second Core asset. The oracle record uses the first public-key entry of a frozen Solana address lookup table as immutable bytes at a verified offset. Core reads it through an Oracle adapter listening only to Burn. The program's supported configuration can be reused across a collection. The test attempts to change the frozen bytes, omit the oracle, remove the plugin as the update authority, and burn as the original or new owner, then checks the actual transfer. This composition requires review of alternative plugin and collection permissions and marketplace tooling before selection.
