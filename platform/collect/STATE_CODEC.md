# B11 source and planning foundation

Implemented: a portable content-addressed source codec, a typed named-command vocabulary, an immutable mint-command builder, and a pure incremental mint plan. The existing full-state `admitMint` and new planner use the same extracted `prepareMintAdmission` decision. No migration, normalized database authority, guarded collection command, quote issuer, HTTP route or capability is implemented by this slice.

## Source records

`createCollectionStateCodec({crypto})` emits canonical UTF-8 JSON records with `{id,size,bytes}`. The ID is SHA-256 of the exact bytes. `encodeReferenceInventory` captures caller state before its first await, preserves published term and draw identities, and returns a compact root plus deduplicated list manifests and pages. Amounts retain the existing `$lamports` representation. `stateDigest` commits to canonical semantic legacy state; it is not a claim that legacy property order or original raw JSON bytes are identical.

- Root: `collection-source-v1`, at most 128 KiB. Source inventory/revision/state digest; header without embedded stages/admissions; up to 32 stage term/eligibility descriptors; admission count and ordered page identities.
- List manifest: `collection-list-v1`, at most 16 KiB. Exact member count, ordered page identities and canonical complete-wallet-list digest. At most 100 pages for 10,000 sorted unique canonical Solana wallets. Equal lists can share one content identity across stages.
- Page: `collection-page-v1`, at most 64 KiB and 100 entries. Eligibility pages use fixed 100-entry groups except the final group. Admissions split by both row count and bytes, with at most 16 pages for 1,000 valid local admissions. This preserves maximum-length finalized proof IDs. Pending free cuts remain explicitly pending; a complete empty list has one empty terminal page.

The separate root bound preserves 32 legal stage rationales containing 500 multibyte characters each. Pages never grow to accommodate a large record. Full legacy conversion/rehydration is an offline/import parity operation, with at most 3,216 pages, 32 list manifests and 32 MiB of retained record bytes. Runtime intake should verify one bounded record at a time. `verifyRecord` verifies byte identity, canonical encoding and bounded record shape; it does **not** independently establish complete graph closure, approved economics, current scope or chain provenance. `decodeReferenceInventory` verifies referenced closure/counts/semantic digest for offline parity. Neither method grants publication authority.

## Required storage boundary

Coordinator migration must store pages/manifests/root immutably, compare an existing ID's exact bytes on replay, and reject conflicting bytes. Unlisted staged records may survive interruption. A final receipt/current pointer may expose a source only after all ordered child identities, counts, kinds and source revision have been verified; no dependent read may see partial intake. Runtime normalized stages/members/admissions must have one declared authority, not compete with legacy aggregate writers. Final receipts carry compact identities and computed deltas, never the full legacy inventory or member arrays.

The measured legacy 32-stage/10,000-wallet/1,000-admission representation exceeds 15 MiB. A single full whitelist exceeds the repository's 256 KiB atomic command limit. These are reasons to normalize and stage the full supported domain, not silently truncate legal input. A future publication repository must separately validate stage policy and current operator authority; format verification alone is insufficient.

## Mint plans

`createMintReservationCommand` binds a wallet, one request key, inventory/stage and the reviewed immutable terms digest. Runtime retry time is excluded from the request digest; caller data is captured before asynchronous hashing and the resulting command is deeply frozen. `collection.reserve-operation.v1` is shared by mint/progression DTOs so a request key cannot quietly become a second operation kind for the same owner. Only the mint builder/planner is executable in this slice; other named DTOs describe later explicit boundaries.

`planMintReservation` consumes repository-supplied facts for one inventory revision: selected stage terms, exact global/stage/wallet admission counts, founder spend, current wallet membership tied to a sealed source identity, duplicate commitment state and any prior operation. These are never HTTP/client assertions. The eventual guarded SQL command must recheck the exact counts, versions, membership, scope, opening dependencies and current clock. Accepted command replay must resolve before planning/expiry/pause checks. The plan contains one admission and count deltas, not a fabricated partial history or full-state rewrite.

The legacy reducer derives these same sufficient facts from its complete history before invoking `prepareMintAdmission`. Full-history parity tests exercise 1,000 admissions across ten stages and compare every exact planned row with the reference transition; existing draw, stage, founder and progression tests remain unchanged. Later storage tests must still prove race safety, no missing children and ambiguous-write reconciliation. Pure parity does not establish atomic authority.

## Governance planning addition

`application/collection-governance.mjs` implements named immutable builders and pure plans for ballot publication, wallet voting and founder decisions. It reuses `openBallot`, `castVote` and `earliestTrancheOpening`. A source binds the exact holder/next-whitelist arrays and opening cut; the canonical union is deduplicated and capped at 10,000 wallets. Publication planning retains the existing `genesis_ballots.snapshot_hash` byte format and emits the same codec's list manifest/pages through `encodeWalletList`. The compact result contains only identities, counts and timing. An empty electorate is a positive empty list, and zero turnout does not erase the founder's decision role.

The vote planner uses only the current wallet's proven frozen membership, prior vote, choice and ballot timing. Those are precisely the fields inspected by `castVote`; other wallets' votes do not change its rule. Full-ballot parity tests exercise this projection. A matching existing vote replays its original time after closing without reopening membership; a changed choice conflicts. The decision plan preserves exact rationale, 48-hour notice and the 7/14/30-day intervals from the previous tranche opening. Ballot turnout does not override those constraints or establish that the previous inventory has sold out.

Still unimplemented: electorate publication authority/receipt, voter membership storage, atomic vote uniqueness, operator scope enforcement, current source revision assertions, decision persistence, unsold-tranche opening guards at storage, HTTP and Worker capability wiring. These helpers are planning-only and cannot publish or admit a command themselves. The future repository must assert these facts under the same atomic boundary and resolve accepted command receipts first.

Combined evidence: `work/b11-governance-tests.log` passes 35 tests, including five new governance tests and the complete foundation/domain/collection regression set. Exact legacy ballot and decision results are compared against disposable Node SQLite; the maximum electorate uses 100 bounded pages. Installed targeted TypeScript and owned-file whitespace checks pass. No migration or storage/HTTP authority code was added.

## Immutable progression quote planning

`application/collection-quotes.mjs` derives an immutable quote and computes an acceptance plan from a stored-quote argument plus fresh participant facts. Both methods capture every caller input before their first asynchronous digest. Quotes bind actor/kind/collection, target/material IDs and versions, exact Season start and participant source digest, policy version, fee, reviewed local ceiling, issue/expiry times and deterministic outcomes digest. Outcomes come from the existing progression and expiry rules. Every upgrade starting Level 1–9 matches the existing Node preview exactly; visual quotes preserve the next fee, completed reroll count and fulfillment-time cooldown semantics.

`maxTotalLamports` is explicitly scoped to `disclosed-local-components-only`: it caps the local protocol-fee components, not a genuinely known transaction total. Network cost has status unknown and null amount; total cost is unknown. All quotes/plans are `local-preview-only` and `executable: false`. The planner cannot issue a stored quote, collect a charge or authorize a transaction.

Acceptance requires the exact reviewed fee/ceiling/expiry and policy, verifies the stored binding, then independently derives the same quote from current owner/reveal/version/lock/counter/trait/expiry facts. Remaining benefit lifetime is recomputed at the original issue time, so elapsed time cannot silently refresh reviewed outcomes. The actual reservation reducer runs at the current server time, including current cooldown and timestamp representability checks. The plan contains only the original quote identity, one domain operation and one/two asset writes; it does not commit them. Accepted command receipt replay must happen before this fresh-admission planner, and the future repository must prove stored quote identity and atomically recheck current facts/expiry/scope.
