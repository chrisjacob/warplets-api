# Private collection source intake

`createCollectionSourceIntake` stages the codec's immutable bytes and verifies bounded list/root closure through `createCollectionSourceRepository`. Node SQLite and local D1 use the same adapter and B02 atomic receipts. Migration035 adds three private tables: records, eligibility-list seals and source-root seals. There is no active-inventory pointer or public intake route.

The three named commands require a current `collection-import` operator scope. Request identity binds the principal, operation kind, record ID, request key and expected revisions. Accepted identical requests replay their original receipt before current scope checks. Changed payloads conflict. A different request key cannot create another operation for an already-staged global identity. Commands independently verify bytes or recompute the proposed seal from retained data; caller-provided approval flags are not trusted.

Each record is stored once as base64 with a compact receipt. Raw limits are 128 KiB for a root, 16 KiB for a list manifest and 64 KiB/100 entries for a page. A list seal reads its manifest and at most 100 exact pages. A root seal reads at most 32 sealed lists and 16 admission pages. Missing, extra, duplicated, reordered, cross-kind or conflicting records cannot seal. Related records remain immutable throughout asynchronous hashing and the final guarded commit. An aborting mandatory-effect trigger prevents an accepted receipt without its child row; lost responses reconcile through the original command identity.

List seals establish canonical complete-wallet-list bytes, ordering, uniqueness, counts and digest. Root seals establish referenced closure and retained admission identities/outcome counts. They explicitly report `verification: record-closure-only`, `semanticStateDigestVerified: false`, `economicsVerified: false` and `provenanceVerified: false`. The declared legacy state digest is an offline parity commitment, not an independently verified runtime approval. Promotion must separately establish policy, provenance, current inventory identity and one mutation authority before replacing legacy writers.

The largest legal codec fixture tested contains 32 distinct lists of 10,000 wallets and 1,000 finalized admissions: 3,245 records and 16,299,312 raw bytes. It seals through list reads no larger than 484,346 bytes and a root read of 1,027,025 bytes; its compact root seal is 11,273 bytes. Actual Node/D1 command acceptance measured at most 14 SQL statements, 22 parameters and 164,115 serialized batch bytes, including a 121,134-byte root. These are local fixture measurements, not production capacity guarantees.

Private recovery includes all three tables and their original receipts. Collection-record recovery pages allow 192 KiB to retain base64-expanded roots, while restore batches remain bounded to 256 KiB. A populated recovery test restored 93 business tables and a 128,774-byte root with a maximum 180,044-byte restore batch, revoked authentication and retained operator revocation. The full maximum graph was not recovery-tested; existing aggregate snapshot limits still apply and explicitly hold oversized snapshots.

Source intake does not publish stages, freeze authoritative eligibility, issue progression quotes, reserve assets, mint, vote or establish on-chain ownership. See [planning foundation](STATE_CODEC.md) and the B11 task card for the remaining mutation boundaries.
