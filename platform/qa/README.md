# Populated local QA

This creates an isolated, synthetic 90-day scenario for reviewing data density,
pagination and user workflows. It does not read or alter the existing manual
demo database, contact external services, generate private keys, or execute
financial transactions. Generated files belong under untracked `work/`; keep them out of commits.

From the repository root, create a **new** directory:

```powershell
node platform/qa/populate.mjs --directory work/qa-three-month-review
node platform/qa/serve.mjs --directory work/qa-three-month-review --port 4181
```

Open `http://127.0.0.1:4181`. The server binds only to loopback. The default owner
is `4nQTuFuY38vevToXAuMwT3nm4SFVfuRRWMEXRm68JeX9`; use `--wallet PUBLIC_ADDRESS`
when generating to select another owner. Sign in normally with that wallet.
Only its public address is used by the generator.

To use an already authorized local tunnel, start the server with its exact
public origin and configure the local tunnel target to port 4181:

```powershell
node platform/qa/serve.mjs --directory work/qa-three-month-review --port 4181 --origin https://app-local.10x.meme
```

This command does not configure or start a tunnel, provision resources, or
deploy. Keep the original manual demo process and database available separately.
The runtime advertises the optional performance and sample-review routes only when their local sources are present. The wrapper strips forwarded identity headers, checks the exact origin on
mutations, adds secure cookies for HTTPS, and shows a synthetic-data banner.
It leaves authentication, session expiration and operational time on the normal
runtime clock. No demo sessions or signing keys are generated by these commands.

## What is populated

The default scenario has:

| Surface | Data |
| --- | --- |
| Tokens | 90 launches over 90 days, matching operational token IDs and detail links |
| Performance | 250 named synthetic participants and about 25,000 distinct reward records |
| NFTs | 183 revealed local assets: 57 for the selected owner, 126 for a large-holder example |
| Mint receipts | One pending owner reservation, plus the fulfilled historical receipts |
| My stakes | 90 owner positions, with accrued and previously harvested units |
| Earn history | 90 submitted contributions, final reviews and final boards; 89 recorded allocations |
| Owner profile | 90 awarded token types, exercising multiple profile pages |
| Leaderboards | Top 100 plus a separate ranked participant outside the top 100 |

The counts for rewards and owner entitlements can vary with the calendar and
configured mint count. `scenario.json` records the exact generated counts,
snapshot timestamp, selected owner, outside-top-100 wallet and rank, price mode,
snapshot bytes and SHA-256 digest. The default data spans **90 days of history**;
it does not create 90 simultaneously active campaigns. Existing ten-day campaign
and admission limits remain enforced by the domain helpers.

`core.sqlite` is built through `seedDemo`, collection reservation/fulfillment and
reveal helpers, market imports, vault manifests, farm observations, and Earn
submission/review/finalization/allocation helpers. The generator does not edit
migrations or bypass settlement invariants. Earn reviews explicitly say they
are synthetic QA reviews, not assessments by AI or a human moderator.

`performance.json` is a separate immutable, dated performance projection:

- The selected owner's awarded, vested and claimed quantities are derived from
  the actual local vault, stake and Earn readers at the snapshot timestamp.
  Harvest fees are explicitly zero in this fixture so gross/net units agree.
  Farm rewards include only emissions accrued by that timestamp, not future
  emissions. Historical harvested units remain part of lifetime awards. Each
  cumulative farm balance is marked `kind: accrual-snapshot`: its timestamp dates
  the balance observation, not a new distribution. These 90 observations still
  contribute quantities and valuations, but are excluded from recent award
  activity, dated award history and milestone evidence. No missing distribution
  dates are invented. The selected owner's dated history therefore covers NFT
  allocations and Earn awards, not the timing of individual staking emissions.
- Other participants have simulated lifetime awards across NFTs, Stake and Earn.
  They do not all have corresponding operational positions or claimable ledger
  balances. The large-holder example has real local collection fixtures, but
  its performance history remains independently simulated.
- Airdrops aggregates the three source categories; it is not a fourth reward
  source. Every reward has one unique ID and one category.
- Live operational vesting continues after generation, so a profile's dated
  claimable quantity can diverge from a later live operational balance. Recreate
  a fresh scenario to refresh the snapshot. Never sum the two datasets.
- Prices are fully synthetic and values are theoretical. The default has complete
  prices so populated totals are visible. Short-lived accepted peaks and explicitly
  rejected bad quotes exercise ATH preservation and quote-quality filtering.

The generator bounds the snapshot to 10 MiB and participants to 150–1000. The
large-holder fixture intentionally exceeds the operational 100-asset automatic
snapshot bound; the existing incomplete/withheld behavior must remain visible
instead of silently treating a truncated ownership set as complete.

## Review sequence

1. Browse Tokens and its detail pages. Check a long catalogue stays readable,
   instructions remain compact, and a detail link resolves to the same token.
2. Connect the selected owner. Browse NFTs, move through inventory pages and
   inspect a pending mint receipt. No settlement or payment is implied.
3. Open Airdrops and My stakes. Compare a few token quantities with the owner's
   profile at the timestamp in the generation report; allow for subsequent vesting.
4. Open Earn to inspect the historical submissions and allocations. This is
   a history/density fixture; only `demo-att` has a fresh short-lived admission
   evidence record on generation. Older synthetic stake evidence is not refreshed
   automatically and must not be presented as current eligibility.
5. Open each category leaderboard. Switch Peak/Market, follow a participant to a
   profile, and use its next-page controls. The generated outside-top-100 address
   is listed under `examples.outsideTop100` in `scenario.json`.
6. Inspect the fixed AI feedback illustration in Attention. The QA server's
   `GET /api/v1/qa/content-review` exposes only the safe creator feedback DTO.
   It evaluates a fixed synthetic example, not the connected owner's submission,
   and never attaches or finalizes moderation in the operational database.
7. Repeat on a narrow viewport and by keyboard. Verify the longer labels, tables,
   empty/unavailable states and pagination do not add horizontal overflow or
   overwhelm the main actions.

## Repeatable variations and checks

Pin the timestamp and seed to reproduce economic quantities and performance JSON:

```powershell
node platform/qa/populate.mjs --directory work/qa-repeatable-one --seed three-month-v1 --as-of 2026-11-13T11:30:48.000Z
node platform/qa/populate.mjs --directory work/qa-price-gaps --seed three-month-v1 --as-of 2026-11-13T11:30:48.000Z --pricing gaps
node --test platform/qa/scenario.test.mjs
```

The gaps variant has one missing-price token and one stale-current-price token.
Any participant with a missing constituent value correctly has an unavailable
aggregate, rather than an understated zero. Historical ATH survives a stale
current quote. The primary scenario deliberately uses complete prices.

## Optional public names and artwork

Keep the generated database and performance snapshot intact. This separate,
explicit refresh fetches free, public, uncredentialed Farcaster profiles and
GeckoTerminal's current 24-hour Solana trending-pool token metadata:

```powershell
node platform/qa/import-public-identities.mjs --directory work/qa-three-month-final-2026-11-13 --output work/qa-public-identities-review
node platform/qa/serve.mjs --directory work/qa-three-month-final-2026-11-13 --port 4181 --origin https://app-local.10x.meme --identity-overlay work/qa-public-identities-review/identities.json
node --test platform/qa/public-identities.test.mjs
```

Use a **new output directory for each refresh**. The importer never opens or
writes `core.sqlite`, changes `performance.json`, or reseeds the scenario.
Names/artwork are presentation samples mapped to existing synthetic IDs. The
selected owner's wallet keeps its own identity. Public people are not presented
as actual 10X users: rows say `demo`, profiles state that their wallet/activity
are simulated, and the QA banner states there is no affiliation or endorsement.
Token artwork likewise does not turn a synthetic Attention Token into the real
source asset. Trading terms, balances, valuation prices and rewards remain the
original synthetic data. Trending pools are a source selection, not a claim that
every token is a memecoin, a recommendation, or the app's performance ranking.

Farcaster samples come from the public following lists of FIDs 3 and 2. The
bounded candidate pool prefers unique accounts with successfully cached raster
images. This is a display sample, not a representative user survey. The importer
retains only username, public display name, FID, profile URL and artwork; it
discards bios, connected-account metadata and real wallet addresses. Token
prices and trading statistics from the source response are discarded too.

`identities.json` pins the economic snapshot digest, retrieval time, source URLs,
response SHA-256 receipts, coverage, failure counts and every cached image digest.
`identities.sha256` pins that manifest. These are local integrity receipts, not
provider signatures. A missing source or rejected image is reported honestly;
uncovered rows keep their synthetic labels/artwork. The refresh performs at most
20 metadata requests, uses four image fetches concurrently, and follows no
redirects. Images must come from the fixed public host allowlist, be PNG/JPEG/
WebP/GIF with matching magic and bounded dimensions (up to 2048 × 2048), fit
256 KiB each and a 32 MiB import cache. SVG, HTML, oversized or unknown images
fall back safely. No image transformation dependency is installed.

Serving is offline: startup verifies the pinned manifest, snapshot mapping and
local raster bytes, then serves only their hashed `/qa-media/` paths. Browsers do
not contact profile/image providers. The local-only manifest endpoint is read
only, has no proxy parameter, and is enabled only by `--identity-overlay`.
Normal Node/Worker runtimes keep their original UI and have no importer route.
See [GeckoTerminal's public API](https://www.geckoterminal.com/dex-api) and the
retrieved source URLs in the manifest for provenance. Public endpoints can change
or become unavailable; refresh failure never modifies the existing scenario.

All output directories must begin `qa-` and must not exist. Overwrites are refused
even if the previous generation was incomplete. Failed generation leaves a
`FAILED.txt` marker; the server refuses to serve it. The server also verifies
the performance digest and refuses a missing database. Rebuild into a new
directory instead of editing or replacing a previous dataset.

Domain-generated operation IDs and proof commitments remain opaque and can vary
between runs. Determinism applies to seeded economic inputs, public synthetic
participant addresses, accepted price observations and performance quantities,
not byte-for-byte SQLite files or receipt IDs.

The tests validate deterministic history, bounds, IDs, quote timestamps,
outside-top-100 lookup, missing prices, overwrite protection, selected-owner
quantity consistency, and actual API pagination across Tokens, NFTs, Stake,
Attention submissions and Earn allocations. This is local QA evidence, not a
production throughput, chain-finality or provider compatibility certification.
