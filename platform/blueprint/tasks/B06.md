# B06 — Share Earn HTTP admission and final moderation across runtimes

**Depends on:** B02 and B05. **PRD:** §§7.1–7.2, 12, 14.1; A35–A38, A41, A44, A53. **Owner:** API/Earn implementer; coordinator reviews generated contracts. [CONTRACTS](../CONTRACTS.md) controls interfaces; consult [storage design](../design/storage-earn.md) section **AE-03**.

## Outcome and inspection

Expose tested application services through Node and local workerd without maintaining two Earn policies. Inspect `platform/earn/{http,openapi,verifiers,workflow}.mjs`, `server/{application,auth,body,api}.mjs`, `edge/src/{worker,wallet,pillars}.ts`, `contracts/{capabilities,shapes,feature-shapes,client}.mjs`, `operator/console.mjs` and current contract tests.

Own proposed `platform/edge/src/earn.ts`, shared HTTP-context/validation helpers, service wiring and cross-runtime contract scenarios. Extend existing paths additively. Do not rename endpoints to match the PRD's proposed catalogue. No public moderator/admin endpoint is introduced here; moderation remains a private local command/console seam with explicit role context.

## Implementation sequence

1. Inject the same application service into both routers. The adapter establishes authenticated principal, origin, clock and quota context; it never accepts wallet identity from submission JSON.
2. Wire existing submission/capacity/action and owner-status reads only after their repositories pass B02. Preserve one submission per token/wallet/epoch, current corresponding stake evidence, staffed capacity and scoped idempotency. Accepted retries must work even after new admissions pause.
3. Port final human review through `recordFinalReview` with moderator identity, score/reason/evidence and expected revision. Identical replay returns the original; changing a published/final review conflicts. The service cannot release tokens. Test it via a private harness, not arbitrary public fixture ingestion.
4. Port signed onboarding completion only through the shared strict proof verifier, prospective issuer grants and nonce uniqueness. Preserve disabled-action behavior and finalized boards. Do not add fake follow completion or social-provider requirements.
5. Keep ordinary and negotiated response schemas exact, including pending reasons, cursor/snapshot scope, fixed-point units and provenance. Advertise Worker routes only after their complete handlers pass; absent collection/quote/notification/transaction routes stay absent.
6. Require explicitly configured staffing/origins in a future hosted profile, but leave actual Worker loopback-only. Code/tests may model Secure cookies and origin settings locally; no domain, remote resource or live configuration is changed.

## Acceptance and commands

A generated-client scenario must run against Node and workerd: message authentication, two competing admissions for the last slot, own submission status, another wallet denied, same-key replay/body conflict, origin/body/expiry errors, paused new admission with successful old replay and final-review conflict. Check malformed/missing evidence yields pending, never fabricated success. Verify ordinary/enveloped DTOs and every advertised route/method. No financial execution flag changes.

Existing checks:

```text
node --test platform/contracts/*.test.mjs platform/earn/workflow.test.mjs platform/earn/verifiers.test.mjs
node platform/contracts/generate.mjs --check
```

Proposed checks, after generating changed schemas:

```text
node --test platform/edge/test/earn-http.test.mjs
pnpm --dir platform/edge typecheck
```

## Completion, limits and recovery

Attach route matrix, exact DTO/command comparison and test results. Bound JSON, pagination and quotas; avoid per-request unbounded cleanup. Current wallet-message authentication is not permission for moderator or financial authority. Hosted physical-wallet/operator identity remains a later gate.

All B work is local emulation: no remote writes, provisioning, payment, public deployment or new probes. Coordinator assigns any additive migration `022+`, preserving `019`. Roll back handler/capability exposure if parity fails, retaining durable accepted receipts and private review records. Never replace unavailable behavior with a stub-success route.
