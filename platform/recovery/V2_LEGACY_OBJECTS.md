# Retained legacy original-object closure

B11-63 adds the private `reconcile-legacy-adoption-closure` phase. It stops at `reconcile-legacy-adoption-aggregate`; it does not authorize readiness or mount a new public route.

The input preparation chain is the verified chain after the last imported stage or original-mint anchor. Each continuation selects the unique retained object whose `prior_chain_digest` equals that chain. This intentionally follows original preparation order: a configured descriptor can discover a child with a key lower than previously processed keys, so globally sorting object keys would not reproduce the accepted preparation chain.

Each object must have canonical private identity, discovery and body JSON, the exact retained body hash and original preparation chain link. The existing `prepareLegacyOriginalObject` verifies retained bytes, role-specific shape and descriptor children. Large historical-control selections use the bounded reuse path described below. A stage or admission discovery must name a retained source identity at its exact index. A policy part must name a previously verified configured descriptor, its exact child identity and that descriptor's processing ordinal. A durable same-key proof cannot be counted again.

After every verified object, the ordinal, accumulated byte count, original preparation chain and independent object proof chain advance in the same atomic checkpoint as its proof. The final continuation checks the terminal preparation digest and both directions of the required-reference set: every stage original, mint original, historical control and descriptor child must exist with the exact identity, and no retained object may be unreferenced. Distinct keys and ordinals, object count and total bytes must equal the accepted certificate's preparation result and quiescence commitment.

Limits remain 2,048 objects and 16 MiB in total, one object per continuation, 64 SQL/object operations, 256 KiB SQL batches, a 128 KiB complete checkpoint, 32 KiB retained phase state and 1 MiB ordinary working data. Actual checkpoint copies, returned rows and original-object verifier buffers are included. An object that cannot fit the combined working bound holds before verification; the adapter does not silently raise that bound or claim an unmeasured maximum historical-control profile.

A historical-control object that would exceed the combined bound during duplicate semantic replay requires an exact same-target `legacy-adoption-control` proof. Its digest binds adoption ID, admission ordinal, anchor body digest, control fact and the same control-selection identity. The matching per-anchor economic proof must also exist. The later aggregate closure verifies the economic proof chain. This path independently rehashes retained bytes, verifies canonical control JSON and reconstructs the exact empty-children object body; it does not accept an opaque completion count. A genuine 84,370-byte selection with 100 usage and 100 spend rows exercises this path on fresh Node and D1/R2 targets. Missing or changed control proof, or absent per-anchor economics, holds.

Per-object checks use phase `legacy-adoption-object`, scope `canonicalJson([adoptionId, objectKey])`, processing ordinal and item count one. Their digest binds adoption ID, ordinal, key, body digest, exact identity and prior/next preparation links. `objectChain` independently commits these checks for the later aggregate closure. Completion retains `objectOrdinal`, `objectBytes`, `objectChain`, `objectResultDigest` and the terminal `chain`.

Acceptance uses genuine source audits, preparation, activation, capture and fresh Node/D1/R2 imports. The configured D1 source uses the installed offline pinned beacon verifier. The manual/configured object-isolation cases explicitly supply the prior recovery-stage/mint/economic/current cursor. The separate large-control case runs those genuine prior phases and persists their actual proofs. Neither case claims full readiness. Fault tests cover missing or corrupt bytes, duplicate chain successors, invalid discovery, repeated keys, omitted proof, lost acknowledgement, wrong reference identity, omitted descriptor references and target mutation.

A separate capacity probe found a 106,770-byte legal control transcript that already exceeds the existing original preparation helper's working bound. This source-preparation limit is outside the tested 84,370-byte accepted-source profile and remains explicit; this milestone does not claim all maximum-length historical control selections can be adopted.
