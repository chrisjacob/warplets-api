# Local financial read projections

The Node app and local Worker share `createFinancialReadService`, named repository reads and the same integer Vault/farm projections. These are observed local fixture accounts. `sourceStatus: local-accounting`, `chainAuthority: unverified`, `unit: base-units` and `executable: false` distinguish them from funded on-chain claim authority. No read creates a transaction intent, deposit or broadcast.

Member Vault reads use one five-statement snapshot: source revision,26 owner page rows,101 owner assets with reveal gates,101 active immutable manifests and at most10001 matching claim rows. The complete summary covers every owner asset, regardless of the displayed page. More than100 assets/manifests, concealed metadata, invalid/future accounting or excessive claim rows withhold all aggregate amounts and the aggregate asset count. SQL suppresses concealed coordinates; the detail query suppresses concealed allocation rows before projection. Detail reads use four statements. Decimal quantities remain strings and all arithmetic remains BigInt; each immutable Season snapshot is prepared once per manifest.

Farm reads fetch at most1001 events per selected farm. The extra row is a bound sentinel: more than1000 events makes the complete read unavailable, rather than simulating a favorable partial history. Owner positions page25 farms plus one continuation row. All repositories reject snapshots exceeding2MiB. These local limits are explicit availability bounds, not claims about chain completeness or production throughput.

Pagination uses opaque context cursors containing route, authenticated owner or public asset identity, source revision, evaluation time and last key. Cursors are read contexts, not authorization tokens; every personalized request independently authenticates its wallet. The server rejects a cursor from another route/owner, a changed revision, an invalid encoding, a future time or an age beyond five minutes. It never treats an old raw asset ID as a current cursor. Each page retains the original evaluation time and snapshot ID.

Migration034 increments the existing source revision on changes to Vault assets, manifests, claims and observations, collection assets, farms and farm events. Unrelated source updates can conservatively expire a cursor too. After projection and asynchronous hashing, the service checks the source revision again. Initial reads retry once on a change; continuation reads require restarting. This preserves a coherent observation rather than combining ownership, reveal and claimed amounts from different revisions. The existing private recovery revision handling remains applicable; no new recovery table is introduced.

All financial responses are `no-store`. Browser restart links remove the stale first-page query before navigating to a fresh read, and the router supports the full bounded cursor length. A restart does not change economic history or claim authority.

Acceptance lives in `vault/read-projection.test.mjs` and `edge/test/financial-reads.test.mjs`. The latter compares actual Node/D1 projections, cursor scope and source-change races, plus public runtime routing. Browser acceptance uses genuine local message authentication and explicitly synthetic ownership observations.
