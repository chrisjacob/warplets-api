# Discovery snapshot pagination

22 October 2026 (Australia/Sydney). Completes the stable-pagination slice of F2 in the [daily product plan](82-next-product-functionality-plan.md). The prior workspace searched the full retained inventory, but displayed at most the first hundred matches. Users can now browse further without changing filters or losing the original ranking cutoff.

## User-visible behavior

- Cards and the compact table show at most **100 tokens per page**, with Previous/Next/Refresh controls above and below the results. Counts show page, range and available matches. Search, date/action/freshness/liquidity/coverage filters still run before pagination; full-view ranks remain intact.
- Later pages use the first page's cutoff and the server's existing snapshot cursor checks. Already loaded pages remain in this browser's memory; Previous and returning to a loaded Next page do not fetch again. A session holds at most five pages within the existing 500-candidate inventory bound.
- Page 1 retains the existing visible-tab sixty-second cached refresh. Automatic refresh pauses on later pages, so it cannot replace their ranking midway through browsing. **Refresh list** reads a new first page and replaces the session only after success. A failed refresh leaves the current successful page visible.
- If the saved inventory changes, a cursor expires, or a page's mode/cutoff/scope/identity cannot be verified, new paging is held. The user sees the last loaded data and an explicit refresh prompt. Pages are never silently concatenated across snapshots. Backward navigation still permits inspection of previously loaded observations.
- The browse cutoff is visible. Scores and table freshness describe that cutoff, not a newly collected market assessment; global source-health/envelope dates retain their separate meaning. A token page or explicit comparison has its own displayed read cutoff. Saving/comparison selections continue across pages by exact mint.
- Cursors and loaded observations are not persisted to browser storage or the shareable URL. Filter/layout/comparison parameters remain shareable; reopening starts at page 1. The separate saved shortlist still persists identities only.

`app/src/discovery/discovery-pager.ts` validates response schemas, expected mode/sort/inventory scope, page size, shared cutoff/counts/scope, distinct mint identities and non-looping continuation cursors. It aborts superseded/disposed requests and prevents delayed responses from an old filter/mode session from appearing in a new one. Page fetch/body reads have a thirty-second abort timeout, preventing an indefinitely busy later page when polling is paused. Explicit setup after cleanup supports React's development remount cycle. Temporary service failures can be retried while preserving the last successful page; expiry/verification failures require a fresh first page.

## API and evidence boundaries

`GET /api/10x/candidates` adds an optional **`browse=inventory`** window. That window reuses `rankedDiscovery`'s existing maximum-500 option, while the per-response `limit` remains 1–100. Omitting it defaults to **`browse=top100`**, preserving the legacy top-hundred window and response size. Scope reports the chosen maximum. The existing 500-candidate / four-megabyte source-input guards still fail rather than trimming a larger inventory. No research allowance or provider quota is increased.

The existing cursor pins every filter, mode, view and browse window, its original scoring time, offset and full filtered-snapshot fingerprint. Workspace offsets can reach later pages within 500 rows. The fingerprint also binds stored-inventory size. Any relevant change returns HTTP 409; the existing five-minute expiration and future-cutoff rejection remain. Older in-flight cursors may require a refresh after the code update. These are ephemeral navigation checks, not signed provenance, persistent study records or proof that the market inventory is complete.

The generated OpenAPI contract changes only the candidate-list route and its two list-response schemas. Legacy full/card arrays remain capped at 100 per response. All frozen v1–v4 evaluators, cohort/election artifacts, source/admission limits, local-calibration authority and evidence/action gates remain unchanged. Reads do not collect providers, enroll studies, prioritize tokens, mutate the database or adopt a new score. No migration, task/supervisor restart or deploy. Production remains thesis-only under the existing client/server flags.
