# Fully locked Jito evaluation

The owner approved evaluating Jito with fully locked rewards on 30 October 2026. The current participation design is approved in [the decision record](approvals/2026-10-30-design.json). The numerical and custody choices below are a **concrete proposal for approval**, not an approved financial configuration.

The machine-readable proposal is [jito-locked-v1-proposal.json](../../packages/meme-protocol/policy/jito-locked-v1-proposal.json). The offline lab consumes that exact file. It has no signer, broadcast path, live account lookup or remote resources.

| Policy          | Proposed configuration                                                                                                                                                                                                                                                                                                                                    |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reward encoding | Every Merkle leaf has `amount_unlocked=0`; the complete entitlement is `amount_locked`. One distributor per immutable daily allocation. Zero allocations remain reserved.                                                                                                                                                                                 |
| Vesting         | Start no earlier than actual launch + release index ×24h, rounding upward to the next whole second if needed. End **one second later**. This gives no payout before release; complete payout becomes available up to just under two seconds after a millisecond-valued release time. Actual chain launch timestamps normally have whole-second precision. |
| Clawback        | One common campaign timestamp: final release's vesting end **+365 days**. After that timestamp, **any signer can trigger clawback**, returning remaining vault tokens to the configured receiver. Claimability is not guaranteed beyond that point. This is not an admin-only action or a promise of indefinite claims.                                   |
| Custody         | Propose a **2-of-3 multisig signing vault** as both distributor admin and owner of the clawback-receiver token account. Actual addresses, signers and multisig execution integration are still required. The admin can change itself and the receiver; these operations need custody review and monitoring.                                               |
| Reserve         | Keep empty/unoffered-round reserves separate. No automatic redistribution, sale or treasury spending. Ultimate destination remains an explicit treasury decision.                                                                                                                                                                                         |
| Pause           | Application controls can stop previews/submissions and new funding. Once funded, valid direct Jito claims cannot be paused by an application flag. This limitation must be accepted for this distributor choice.                                                                                                                                          |
| Recovery        | Persist the allocation ID, hashes, root and u64 distributor version before submission. Read back the actual account owner/program, mint, root, amounts, timestamps, admin, receiver and vault before any later funding. A failed creation must never cause blind funding of an account found at the expected PDA.                                         |

The code rejects non-final allocations, total mismatches, duplicate claimants, nonzero unlocked rewards, invalid integer encodings, and preparation at/after vesting start. The pinned program requires future vesting timestamps at creation, so a delayed settlement needs an approved recovery schedule; the planner does not silently move a historical release. A random, persisted version nonce is recommended for the later transaction lifecycle; retries must reuse the same nonce and must not generate a new intent automatically.

## Evidence and tests

The evaluation pins Jito source commit `2cf79f63973a79e6354871dc9355a63aa1d15139`. Reviewed IDL SHA-256: `607bd0864aaa53a278c4c58372f11d0cd3c705de7110974d265d0c573ec5c29f`; locked-claim state source SHA-256: `1c721d0bb3f78634881c05a104500a85092f8aa8001c6355acac31c36053f040`. The program and IDL use a **u64 version**. An older generated Python helper in the same repository uses u8 and must not be used as the wire-format authority.

Run `pnpm --dir packages/meme-protocol check`. Tests compare roots and every proof with the pinned upstream three-recipient vector; verify instruction discriminators, u64 encoding and account order; cover all ten release times, rounding, zero early payout, exact withdrawal arithmetic and repeat-withdrawal previews; reject altered read-back authorities; and serialize a top-100 claim's initialize/withdraw pair within the Solana packet size. These are offline compatibility and arithmetic checks, not executed program tests or a transaction-cost estimate. A later claim-all journey may require several transactions and actual chain observations between retries.

The prototype creates unsigned `new_distributor`, `new_claim` and `claim_locked` instructions. It does not create or fund an account. No Jito program code has been copied into the application. The upstream fixture is public compatibility data with provenance; program/license assessment remains a production prerequisite.

Primary evidence: [clawback is permissionless after its timestamp](https://github.com/jito-foundation/distributor/blob/2cf79f63973a79e6354871dc9355a63aa1d15139/programs/merkle-distributor/src/instructions/clawback.rs), [locked vesting arithmetic](https://github.com/jito-foundation/distributor/blob/2cf79f63973a79e6354871dc9355a63aa1d15139/programs/merkle-distributor/src/state/claim_status.rs), [initialization IDL and front-running warning](https://github.com/jito-foundation/distributor/blob/2cf79f63973a79e6354871dc9355a63aa1d15139/programs/merkle-distributor/idl/merkle_distributor.json).

Next gate: approve or amend the proposed interval, deadline and custody policy; identify the real custody accounts; then execute the pinned program in a compatible validator/SVM and verify initialization, funding, pre-release rejection, claim-status retries, double withdrawal, underfunding, authority changes, permissionless clawback, costs and interrupted transactions. Deployment and financial activation require separate authorization after those checks.
