# Discovery read performance and security

23 October 2026, Australia/Sydney. Review of the current local Discovery implementation, including [170](170-cached-event-sample-evidence.md). No deploy.

## Findings and changes

- [x] **Repeated accepted-receipt queries and replay.** GMGN review loaded a reservation's request separately from the same hash-verified receipt, for both activity and original trader selection. Accepted reads now use the existing combined receipt/request reader. Missing, pending, failed and legacy states retain their explicit behavior; original request/response/receipt/report hashes are still checked. The two-selected-transaction sample drops from six SQL reads to four. No database/global memoization or change to collector accounting.
- [x] **Repeated sample validation inside one request.** The cache reader planned the complete source and then replayed it again for comparison. Request-scoped preparation now validates the whole source/selection once, captures private copies and exposes a separate plan copy plus a single-use comparison function. Caller mutation cannot replace that captured source/plan, and a consumed preparation cannot be reused. All cache validation, byte/complexity bounds and exact comparison rules remain. Standalone imports and archived replay still revalidate their own complete input. Versions, field order, output hashes and scoring effect are unchanged.
- [x] **Oversized cached-body materialization.** The 1.8 MB combined cache limit was checked after D1 had returned each body. A SQL `CASE` now returns null for a body exceeding the remaining budget, along with its actual byte count. The reader rejects it without copying the oversized payload into Worker memory, parsing it, replacing a signature or returning partial support. The existing bound is unchanged.
- [x] **Foreign-browser local GET work.** Admin origin/token protections were already present, but local report GETs could still be triggered by foreign browser resources despite same-origin response protections. GET admission now rejects foreign/null Origin and unverified cross-site/same-site Fetch Metadata before identity dispatch or database work. Same-origin/navigation, headerless CLI and explicitly trusted preview origins remain supported. This is browser-origin resource protection, not authentication for an exposed public service. Existing loopback/local-only gates, admin authentication and production release flag remain required.
- [x] **Unbounded browser JSON transport.** Shared Discovery reads and the explicit admin operation UI consumed `response.json()` without an application response budget. Both now use a streaming reader capped at 8,000,000 received bytes, 4,096 fragments including empty fragments, 100,000 JSON nodes / 64 levels before schema validation, and a 20-second transport/read/decode deadline (60 seconds for explicit POST operations). Advertised lengths are checked but never trusted instead of actual bytes. A bounded growing buffer avoids retaining one object per fragment; split UTF-8 is decoded correctly. Failed/oversized/stalled/aborted streams are cancelled, locks/listeners/timers cleaned up, and malformed JSON/encoding errors exclude raw response text. Caller schema validation and last-good-view behavior remain. Operation methods, headers, bodies and IDs are preserved; no automatic retry. A timeout is an unknown operation outcome, and the admin view directs the operator to inspect Data status before retrying.

The browser transport budget is separate from provider quotas and evidence admission. It neither truncates data into a passing result nor changes server-side collection limits. An over-bound response fails visibly; it cannot earn coverage, safety, organic-volume or score credit.

## Performance evidence

A read-only interleaved benchmark compared committed original code with the revised reader against the same frozen accepted 50-event page and original cutoff. All 30 reports per version match the frozen report exactly. Original median/p95: **95.191 / 107.829 ms**; revised: **82.358 / 90.792 ms**. Median reduction is approximately **13.5%**; SQL reads fall **33.3%**, from six to four. No provider requests or database writes.

The first change, removing only duplicate SQL reads, showed no local latency improvement (90.259 versus 93.665 ms median), which motivated removing the repeated in-request replay. These are local Node/SQLite measurements of one cache-missing sample, not production D1 latency, Worker CPU/billing, broad-token performance or Core Web Vitals. Serving149 stays open. No cross-request cache is introduced to obtain the improvement.

## Validation and remaining work

Final verification passed: 1,548 backend tests / 105 suites, 215 Discovery UI tests / 42 suites, both typechecks, the closed app build, performance budget (227.8 KiB gzip across 11 startup chunks), thesis-only release guard and security preflight. The first full backend run exposed two direct-handler error-response cases; these were fixed, the affected 32 guard/read-model tests passed, and the complete rerun passed without changing timeouts or evidence thresholds. Live Worker admission returned 200 for normal/trusted-preview reads and the existing Vite proxy, and 403 for foreign Origin and foreign embeds. The live sample endpoint returned 200 in 264 ms and matched the original 169 report at its new cutoff. Isolated browser checks passed at 1280, 390 and 320 pixels with no overflow, unexpected requests or browser errors, preserving keyboard, identity, error-retention and cancellation behavior. Regression cases cover foreign/browser reads rejected before DB work; unchanged accepted-report hashes and legacy replay; two SQL receipt reads; one in-request source replay; private-copy mutation/reuse rejection; null oversized-body projection; full-byte-ceiling JSON; streamed/advertised/fragmented oversize; stalled headers/body; caller/late-body cancellation; split/invalid UTF-8; malformed JSON/schema rejection; JSON node/depth limits before schema work; and explicit operator identity/body preservation without retry.

Workers guidance and current types 5.20261022.1 were checked against the [official best-practices reference](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/). No binding, dependency or configuration changes. Chrome DevTools MCP is unavailable; existing isolated browser checks provide behavioral/reflow evidence, not a Lighthouse/Core Web Vitals audit.

Preserve all original private artifacts, source receipts, proof rows and manifests. No new provider/RPC collection, allowance changes, backoff resets, spent-hour reopening, migration, runtime restart or deployment. The sample collector remains disconnected; production remains thesis-only. Remaining priorities are the journaled operator-only sample collector, real prospective shortlist reviews/follow-ups, qualified holder observations, authoritative completed-ATTN exclusions and enabled serving/security acceptance. These fixes do not close those product/evidence gates.
