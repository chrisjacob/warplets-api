# 142 — Automatic wallet selection across original stages

22 October 2026. Extends [141's isolated wallet turn](141-recorded-wallet-snapshot-cycle.md) to the original automatic scheduler, without a pinned mint. The unchanged `runWalletCycle` chooses among competing cached, refresh, direct funding, reader recovery and new-snapshot work. ## Selection and retained identities

`runRecordedAutomaticWalletCycleOnEvidenceTarget` has a strict request with no address field. It retains the original enabled/time/wallet/shared limits, ten control/workflow UUIDs, ordinary-write UUIDs and per-response wallet/RPC publication pairs. Optional receipt stage identity and required checkpoint/recovery identity lists supply only the existing bounds: twenty direct checkpoints, two recovered bodies and eighteen recorded responses. Required identities for the selected stage must exist before acquisition. All identities are unique across domains; duplicate checkpoint wallet/anchor tuples also hold. All input/context is copied before asynchronous IO. No caller URL, fetch delegate, callback to an oracle or winning-mint override is accepted.

A private admission preview mirrors the original scheduler's selection block using the original shortlist, contender predicate, planner and comparator. It validates work first, then reads attempts, filters original contender/age/risk and due-attempt conditions, takes the first **twenty before excluding source-limited/invalid plans**, and retains original stage/cost/attempt/potential tie-breaking. Cached progress keeps its original priority. Retry equality is due; a later retry time is skipped. The original active index still has its existing five-hundred-row bound and shortlist cap. No ranking, liquidity/age/risk policy or collection allowance changes.

The preview selects a publication context and checks the necessary authenticated receipts/checkpoint/recovery/stage identities. It does not execute the wallet turn. The original scheduler then acquires its own unchanged lease and performs its own automatic selection, with `address=undefined`; it is not rerun with the preview's mint as an explicit override. Its original rapid-pacing predicate is preserved, including zero-row busy, exact-expiry and not-due lease outcomes.

The lease plan records the selected mint's existing context. With no selected candidate, the control-only context is `automatic-empty`; that marker is never a candidate, receipt, profile, quota or source request. The original scheduler still acquires/releases and returns empty. Disabled, paused and shared-backoff outcomes return before preview/acquisition. Source-admission or missing-identity failures may safely hold before an original lease attempt; they are not represented as original empty/waiting success.

## Planning consistency and execution

Admission records SHA-256 pins for each exact fixed planning selector/binding/result. Only digests and distinct selector keys survive in this in-memory map, with a bounded 16,384-key capacity. Repeated reads must agree. The authoritative scheduler rereads native state after acquisition; each result must match its admission pin, and every pinned selector must have been observed before any catch-up reservation, pacing write or source work. The complete active-candidate index is reread and pinned again at that boundary. All reads retain the current native append-owner fence and authenticated old/new receipt contract.

A changed attempt, checkpoint, transaction cache or candidate index cannot silently choose another mint after admission. Such a mismatch holds with no recorded dispatch, quota charge, run row or reassignment. If acquisition already committed, its historical plan remains and its original lease expires normally; the adapter does not reset ownership or invent a cleanup job. Unsupported/read-admission errors cannot be swallowed by the original planner into an apparently supported alternative: subsequent writes are withheld. This deliberately conservative race behavior is additional admission, not evidence freshness or action authority.

After verified selection, existing exact publication domains execute the original chosen branch. Cached funding uses the original checkpoint CAS and atomic four-statement completion batch. Direct funding, reader recovery and snapshots reuse their established source, paired-spend, catch-up, unsupported/backoff, immutable receipt and completion/failure paths. Existing original guards still decide zero-row races. Snapshot cohorts remain a separate post-commit operation; inspect the producer and cohort outcomes independently. Earlier cache/checkpoint work and spent allowances survive later failure, as before.

Every recorded response still requires fresh accepted original quota reservations and current dispatch authority. Recovered counters/claims/leases are history, not request permits. All outcomes retain `source_authorized=false`, zero real provider requests and false runtime/action/evidence/Free acceptance flags. The preview's selection diagnostics describe this bounded scheduling turn, not token quality, complete market attention or a recommendation.

## Outcomes and recovery boundary

Inspect `result`, all `publications`, `selection.selected`, `selection.considered`, `selection.verified` and existing producer/cohort/post_commit fields. A committed acquisition that declined the lease can have a preview but `verified=false`; no authoritative selection was completed. Once verified, that historical fact survives a later held outcome, including append-owner loss after quota reservation. It grants no current ownership or dispatch permission. Future fault tests must assert selection history and current authority separately. `completed` means the original caller returned, including failure, waiting, empty or disabled. `held` identifies unsupported or unconfirmed admission/publication, preserving any earlier accepted history.

Known publication IDs still support explicit pending execution under the exact original append grant or current-owner read-only reconciliation of committed history. No new plan kind, target schema, intent format, provider cap or old receipt format is introduced. An unknown lease acknowledgement cannot authorize selection/source work, and read-only reconciliation never repeats it.

The selection pins are intentionally in-memory. They do **not** certify restart/resumption of the whole scheduler, automatic cohort retry, new-generation adoption or resurrection of an old job. Required identities and recorded input must be retained; do not recover a whole turn by rerunning the scheduler, replacing IDs, refunding counters or reviving a lease. Durable whole-workflow progress and explicit cohort recovery are next.
