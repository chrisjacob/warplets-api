Only the original planner's `new_snapshot` or `refresh_required` stage is admitted before lease acquisition. Other stages hold; disabled, pause, shared-backoff and busy outcomes retain their original behavior.

The unchanged collector handles genesis, creation/curve history, early/recent transactions, preserved prior buyer anchors, direct and second-hop funding, holder input and dated severe-loss review associations. Its transaction/sample/byte limits, original decoder, original history gaps, unsupported-reader bookkeeping, current reader/version rules and evidence analysis remain. Finalized curve pages are reused only under the original verified-creation predicate. This adapter does not expand provider limits or buy another response on reconciliation.

Holder input resolves through the existing authenticated frozen/new receipt reader, complete frozen-source admission and a final target/owner/selection check after asynchronous IO. The added fixed native review selector retains original latest-per-day ordering and thirty-day/maximum-thirty selection. It checks each result's byte size and aggregate size before loading text, preserves exact UTF-8/BOM/NUL through BLOB decoding and never silently truncates. Malformed reports retain the original schema failure. No generic SQL reader or caller transport delegate is exposed.

Every recorded dispatch requires fresh accepted original wallet-then-shared-RPC quota results and a current accepted lease. A separate snapshot guard pins the complete original candidate payload as well as its nullable prior wallet evidence hash, so new tokens with no prior analysis remain protected. Current append grant, wallet lease/strict expiry, pause and shared RPC backoff are rechecked before reservations and recorded responses. A candidate/lease/shared-state change after counters commit withholds the response without refund. All response bodies are supplied strings, and every outcome retains `source_authorized=false` and zero real provider requests.

## Atomic snapshot publication

The separate strict `wallet_snapshot_cycle` domain binds the original accepted acquisition, job, candidate payload pin, nullable prior evidence hash, original quota limits, exact ordered operations and optional authenticated receipt ticket. It admits only the original catch-up/backoff/unsupported/failed-run statements, or the entire original successful snapshot batch. Existing receipt, direct, recovery and other result/plan contracts stay unchanged. Only catch-up returns a bounded eighteen-unit `{used}` row; snapshot receipt and other result positions remain empty arrays.

Before staging a successful batch, the TypeScript publisher parses the original wallet input, reruns the original analyzer and requires exactly matching candidate analysis. Native checks bind the staged mint/hash/time/body to that analysis, every exact profile row to its original wallet/hash/time, and original job/run/attempt/release/work bindings. The ticket remains a separate stable identity and is authenticated before encrypted intent readiness. SQL only executes from the persisted immutable plan after readiness sync.

Successful publication rechecks the original candidate pin, current lease and shared state inside the native transaction. Receipt/reference, run, candidate wallet analysis, attempt pacing, owner-conditioned lease release, work deletion and all profiles commit together. A later-statement failure rolls them all back while earlier ordinary transaction/checkpoint writes and charged counters survive. Failure bookkeeping preserves original snapshot-kind/source-hash/RPC-call semantics, including a null prior hash for a new candidate. No timestamp, source qualification or score gate is invented by the adapter.

Known-ID recovery validates the original parent grant and committed results. A current append owner may reconcile committed history after transfer, but cannot execute a former owner's pending intent. Reconciliation neither grants a new recorded response nor reacquires the historical job. Target schema, journal encryption format and all frozen original artifacts remain unchanged.

## Cohorts and outcomes

After the snapshot SQL commits, the original caller rereads the candidate and invokes unchanged cohort capture. Only the exact original first-observation, first-wallet-sample and first-recommendation statements reach the existing fixed cohort writer, with the successful snapshot publication as parent. This is a separate atomic post-commit operation, preserving original first-row/idempotence semantics.

Inspect **all** of `result`, `publications`, `producer`, `cohort` and top-level `post_commit`. `state=completed` means the original scheduler returned, including disabled/waiting/failed outcomes. A cohort failure returns original failed bookkeeping while `producer.state=committed`, `cohort=unconfirmed` and `post_commit=failed`; the already-saved evidence is not represented as rolled back. Lost producer acknowledgement leaves an explicitly held producer and no cohort attempt even when the SQL actually committed. Known-ID reconciliation reveals that history read-only; it does not rerun cohorts or certify whole-turn retry. The producer publication's own callback status remains separate from the cycle's cohort status.

Whole-workflow recovery and automatic cohort retry are still open. Retain identities/context and reconcile known publications explicitly; do not rerun the original scheduler as a recovery mechanism, reconstruct new stage/write positions, reuse spent reservations or reactivate an old job. No automatic selection, live transport, runtime adoption or release authority follows from these helpers.
